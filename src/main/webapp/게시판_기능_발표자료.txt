게시판 기능 구현 발표 자료
========================================
기준 소스: BoardController.java, BoardService.java, BoardDAO.java, BoardDTO.java, BoardCommentDTO.java, BoardFileDTO.java (제공된 6개 파일)
목적: PPT 슬라이드 구성 및 발표 대본 초안
주의: 실제 JSP 화면, DB DDL, 실행 결과는 제공되지 않았으므로 아래 설명은 Java 코드에서 확인되는 구현에 한정합니다.

[슬라이드 1] 게시판 기능 소개
■ PPT 핵심 내용
- 공지사항(NOTICE), 자료실(RESOURCE), 자유게시판(FREE) 분류
- 게시글 CRUD, 검색·페이징, 댓글·답글, 첨부파일 기능
- 로그인 사용자 및 관리자 권한에 따른 기능 제한
■ 발표 멘트
“저희 게시판은 공지사항, 자료실, 자유게시판으로 구분됩니다. 게시글 작성과 조회뿐 아니라 검색, 댓글, 파일 첨부 및 권한 검증까지 구현했습니다.”

[슬라이드 2] 전체 구조와 요청 흐름
■ PPT 핵심 내용
- JSP 화면 ↔ BoardController(Servlet) ↔ BoardService ↔ BoardDAO(JDBC) ↔ DB
- BoardDTO, BoardCommentDTO, BoardFileDTO: 계층 사이 데이터 전달
- Controller는 URL 분기·입력·권한·응답 처리, DAO는 SQL 실행
- 주의: 모든 기능이 Service를 거치는 것은 아님. Controller가 DAO를 직접 호출하는 경로도 존재
■ 발표 멘트
“화면에서 요청이 발생하면 Servlet인 BoardController가 처리 경로를 결정합니다. 목록 조회와 페이지 계산은 Service를 활용하며, 등록·댓글·첨부파일 등 여러 기능은 Controller가 DAO를 직접 호출합니다. DAO는 JDBC로 DB에 접근하고 DTO가 데이터를 전달합니다.”

[슬라이드 3] 6개 Java 파일의 역할
■ PPT 핵심 내용
1. BoardController: GET/POST 요청, 화면 이동, 인증·권한 확인, 파일 처리
2. BoardService: 목록 조회, 총 개수, 페이지 수 계산, 분류 검사
3. BoardDAO: 게시글·댓글·파일 SQL 처리 및 회원 상태 확인
4. BoardDTO: 게시글 번호, 회원 번호, 분류, 제목, 본문, 태그, 조회 수, 작성·수정 시각, 작성자, 댓글 수
5. BoardCommentDTO: 댓글 번호, 게시글 번호, 작성자, 부모 댓글 번호, 내용, 작성 시각, 게시글 제목
6. BoardFileDTO: 파일 번호, 원본명, 저장명, 저장 경로, 크기, MIME 타입
■ 발표 멘트
“기능별로 책임을 분리해 소스를 구성했습니다. DTO는 데이터를 보관하고 DAO는 SQL을 실행하며 Controller가 요청과 응답을 담당합니다.”

[슬라이드 4] 게시글 목록·상세 조회
■ PPT 핵심 내용
- GET /board 또는 /board/list → showList()
- category, q, page 파라미터 처리
- service.count() 및 service.findPage()로 목록 조회
- GET /board/detail?id=... → showDetail()
- 상세 조회 시 조회 수 증가, 댓글 목록 및 첨부파일 목록 함께 로딩
- /board/list?id=... 경로에서는 목록 화면 안에 선택 게시글 정보도 제공
■ 발표 멘트
“목록 화면에서는 카테고리, 검색어, 페이지 번호에 따라 데이터를 조회합니다. 상세 화면에 들어가면 조회 수를 증가시키고 댓글과 첨부파일도 함께 가져옵니다.”

[슬라이드 5] 게시글 작성(Create)
■ PPT 핵심 내용
- GET /board/write: 로그인 여부 확인 후 작성 화면 이동
- POST /board/create: 로그인 및 활성 회원 상태 확인
- category, title, content, tags 입력값 검사
- dao.insert()로 저장 후 생성된 boardId 반환
- 첨부파일이 있으면 저장하고 상세 화면으로 이동
- NOTICE 분류 작성은 관리자만 가능
■ 발표 멘트
“로그인한 활성 회원만 글을 작성할 수 있습니다. 제목은 1~200자, 본문은 필수, 태그는 최대 500자이며 공지사항 등록은 관리자에게만 허용합니다.”

[슬라이드 6] 게시글 수정·삭제(Update/Delete)
■ PPT 핵심 내용
- GET /board/edit?id=... → 수정 화면
- POST /board/update → 기존 글 조회, 작성자 또는 관리자 권한 확인, 내용 갱신
- POST /board/delete → 권한 확인 후 논리 삭제
- UPDATE board SET is_deleted=TRUE, deleted_at=CURRENT_TIMESTAMP
- 일반 회원은 본인 글만 수정·삭제, 관리자는 타인 글도 관리 가능
- 관리자 수정 시에도 원래 작성자(memberId)는 유지
■ 발표 멘트
“수정과 삭제에는 작성자 검증을 적용했습니다. 삭제는 실제 DB 행을 지우지 않고 삭제 여부를 변경하는 소프트 삭제 방식으로 구현했습니다.”

[슬라이드 7] 검색과 페이징
■ PPT 핵심 내용
- PAGE_SIZE = 10: 페이지당 게시글 10개
- offset = (page - 1) × 10
- pageCount = max(1, (total + 9) / 10)
- 제목, 본문, 태그, 작성자 이름을 LIKE로 검색
- 카테고리별 검색 및 최신 작성 순 정렬
- SQL LIMIT ? OFFSET ? 사용
■ 발표 멘트
“게시글이 많아져도 한 번에 10개씩 조회하도록 페이징했습니다. 검색은 제목뿐 아니라 본문, 태그, 작성자 이름까지 지원합니다.”

[슬라이드 8] 댓글 및 대댓글
■ PPT 핵심 내용
- POST /board/comment → 댓글 등록
- parentCommentId가 null이면 일반 댓글, 값이 있으면 답글
- 답글 대상 댓글이 해당 게시글에 존재하는지 검증
- 댓글 내용은 1~2000자
- POST /board/comment/delete → 본인 댓글 또는 관리자 삭제
- 댓글도 is_deleted=TRUE 방식으로 논리 삭제
■ 발표 멘트
“댓글은 부모 댓글 번호를 선택적으로 저장하는 구조입니다. 이 값을 이용해 일반 댓글과 답글을 구분하며, 다른 게시글의 댓글에 잘못 답글을 다는 상황도 검사합니다.”

[슬라이드 9] 첨부파일 업로드·다운로드
■ PPT 핵심 내용
- @MultipartConfig: 파일당 최대 10MB, 요청 전체 최대 40MB
- 업로드 파일 수 최대 5개
- 허용 확장자: pdf, png, jpg, jpeg, gif, txt, csv, doc, docx, xls, xlsx, ppt, pptx, zip
- UUID로 서버 저장 파일명 생성, 원본명과 메타데이터는 DB 기록
- 저장 경로: /WEB-INF/uploads/board
- GET /board/file?id=... → 파일 메타데이터 조회 후 다운로드 응답
■ 발표 멘트
“첨부파일은 파일 형식과 크기, 개수를 제한합니다. 서버에는 UUID 이름으로 저장하고 DB에는 원본 파일명과 저장 경로를 보관합니다. 다운로드할 때는 원본 파일명을 응답 헤더에 넣습니다.”

[슬라이드 10] 로그인·권한·보안
■ PPT 핵심 내용
- POST 요청은 CSRF 토큰 검사, 실패 시 403
- 글쓰기·수정·삭제·댓글 작업 시 로그인 및 ACTIVE 회원 여부 검사
- 작성자 또는 관리자 여부 확인(canEdit)
- 공지사항 등록·변경은 관리자 권한 필요
- PreparedStatement의 바인딩 파라미터 사용
- 파일 다운로드 시 canonical path를 이용해 경로 이탈 방지 검사
- 잘못된 요청값은 400, 권한 없음은 403, 대상 없음은 404 처리
■ 발표 멘트
“단순히 기능을 제공하는 데 그치지 않고 CSRF 검증, 회원 상태 확인, 작성자 권한 확인을 적용했습니다. SQL은 PreparedStatement로 실행하며 다운로드 경로도 검증합니다.”

[슬라이드 11] DB 처리의 핵심
■ PPT 핵심 내용
- board: 게시글 데이터와 is_deleted, view_count 관리
- board_comment: 댓글·답글 및 삭제 여부 관리
- board_file: 첨부파일 메타데이터 관리
- member: 회원 이름, 상태, 회원 ID 조회에 사용
- JOIN으로 작성자 이름 조회; 탈퇴 회원은 '탈퇴한 회원' 표시
- JDBC DataSource + try-with-resources로 연결·쿼리 자원 관리
■ 발표 멘트
“DAO에서는 게시글, 댓글, 파일, 회원 데이터를 SQL로 연계합니다. 탈퇴한 회원의 글도 작성자 이름을 ‘탈퇴한 회원’으로 표시하도록 처리했습니다.”

[슬라이드 12] 구현 특징 및 마무리
■ PPT 핵심 내용
- 카테고리별 게시판과 CRUD를 하나의 구조로 통합
- 검색·페이징으로 목록 사용성 확보
- 댓글·답글과 파일 첨부로 상호작용 지원
- 인증, 권한 검사, 소프트 삭제 등 운영 요소 반영
- 향후 검토: Controller/DAO 역할 분리 개선, 업로드·DB 저장의 트랜잭션 일관성, 파일 콘텐츠 검증 및 운영 테스트
■ 발표 멘트
“이번 게시판은 기본 CRUD에 댓글과 첨부파일, 권한 검증까지 결합한 기능입니다. 이후에는 서비스 계층으로 업무 로직을 더 분리하고, 업로드 실패 시 데이터 정합성을 보장하는 구조를 보완할 수 있습니다.”

GET  /board/file            첨부파일 다운로드

[예상 질문 및 답변]
Q1. 왜 게시글을 실제로 삭제하지 않나요?
A. DAO에서 is_deleted 값을 TRUE로 바꾸는 소프트 삭제를 사용합니다. 일반 조회에서는 삭제된 글을 제외합니다.

Q2. 페이징은 어떻게 계산하나요?
A. 페이지당 10건으로 설정하고 (page-1)*10을 OFFSET에 사용합니다. 전체 건수로 페이지 수를 계산합니다.

Q3. 일반 사용자가 다른 사람의 글을 수정할 수 있나요?
A. Controller의 canEdit()에서 관리자이거나 작성자 본인인지 확인합니다. DAO UPDATE에도 member_id 조건이 들어갑니다.

Q4. 답글은 어떻게 구분하나요?
A. BoardCommentDTO의 parentCommentId와 board_comment.parent_comment_id를 사용합니다. null이면 일반 댓글입니다.

Q5. 파일명 중복은 어떻게 방지하나요?
A. 서버 저장 이름을 UUID로 생성합니다. 원본 파일명은 별도로 저장해 다운로드할 때 사용합니다.

Q6. Controller와 Service는 완전히 분리되어 있나요?
A. 아닙니다. 목록·페이징 등은 Service를 이용하지만 여러 등록·수정·댓글 기능은 Controller에서 DAO를 직접 호출합니다. 리팩터링 가능한 부분입니다.

[발표 시 주의 사항]
- 실제 화면 디자인, DB 테이블 생성문, 테스트 성공 여부는 이 6개 파일만으로 확인할 수 없습니다.
- 파일 업로드가 악성 파일을 완벽히 차단한다고 설명하지 마세요. 현재 코드에서는 확장자·크기·개수 검사 중심입니다.
- 전체 요청 최대 40MB와 개별 파일 최대 10MB, 최대 5개 제한을 구분하세요.
- 서비스 계층이 모든 비즈니스 로직을 처리한다고 말하지 마세요.
- 댓글 수정 기능은 제공된 Controller에 구현되어 있지 않습니다. 댓글 등록·조회·삭제를 중심으로 설명하세요.
