주제: 웹 프로젝트 회원가입 및 회원정보 수정 기능 구현

============================================================
1. 인사 및 담당 역할 소개
============================================================
안녕하세요. 저는 이번 웹 프로젝트에서 회원 관리 기능 중 회원가입과 회원정보 수정을 중심으로 담당했습니다.

회원가입은 사용자가 사이트에 새로운 계정을 만들 수 있도록 하는 기능이고, 회원정보 수정은 가입한 사용자가 자신의 이름, 이메일, 연락처, 주소 등을 변경할 수 있도록 하는 기능입니다.

두 기능 모두 사용자 입력을 받아 검증하고, 데이터베이스에 안전하게 저장하거나 변경하는 과정이 중요하기 때문에 Controller, Service, DAO, DTO를 구분하여 구현했습니다.

============================================================
2. 회원 기능의 전체 구조
============================================================
저는 Java Servlet과 JSP를 사용하는 MVC 기반 구조로 회원 기능을 제작했습니다.

사용자가 웹페이지에서 정보 수정을 요청하면 MemberController가 요청을 받습니다. Controller는 전달된 데이터를 MemberService로 넘기고, Service에서는 필수 입력 여부와 데이터 형식, 중복 여부 등을 검사합니다.

검증을 통과하면 MemberDAO가 JDBC를 사용해 데이터베이스에 INSERT 또는 UPDATE SQL을 실행합니다. 조회한 회원정보는 MemberDTO 객체로 전달할 수 있습니다.

즉, Controller는 요청과 화면 이동, Service는 검증과 업무 처리, DAO는 데이터베이스 접근, DTO는 회원정보 전달을 담당합니다.

[발표 화면 시연 포인트]
회원가입 화면과 마이페이지의 회원정보 수정 화면을 보여주면서 흐름을 설명합니다.

3. 회원가입 기능 설명
============================================================
먼저 회원가입 기능입니다.

사용자가 회원가입 화면에서 아이디, 비밀번호, 비밀번호 확인, 이름, 휴대폰 번호, 이메일, 우편번호, 주소, 상세주소를 입력하고 필수 약관에 동의하면 회원가입 요청이 전달됩니다.

MemberController는 /member/signupPro.do 요청에서 입력값을 받아 필수 약관 동의를 확인한 뒤 MemberService의 signup() 메서드를 호출하면, Service에서는 다음과 같은 조건을 검사합니다.

첫째, 아이디는 영문 소문자와 숫자를 모두 포함한 6~20자로 제한하고, 데이터베이스에 이미 존재하는 아이디인지 확인합니다.

둘째, 비밀번호는 영문, 숫자, 특수문자를 포함한 8~50자로 검사하고 비밀번호 확인 값과 일치하는지 확인합니다.

셋째, 이름은 필수이며 50자를 넘지 않도록 검사합니다.

넷째, 휴대폰 번호와 이메일은 정해진 형식에 맞는지 검사하고, 이메일 중복 여부도 확인합니다.

다섯째, 우편번호가 입력된 경우 숫자 5자리인지 검사하며, 주소와 상세주소는 각각 255자 이내인지 확인합니다.

검증 과정에서 문제가 발견되면 Service가 오류 코드를 반환합니다. Controller는 해당 오류 코드에 맞는 한국어 메시지를 보여주고, 비밀번호를 제외한 기존 입력값을 다시 화면에 전달하여 사용자가 수정할 수 있도록 합니다.

모든 검증을 통과하면 DAO의 insertMember()를 호출해 member 테이블에 데이터를 저장합니다. 정상 등록되면 로그인 페이지로 이동합니다.

[핵심 코드]
MemberController: memberService.signup(...)
MemberService: signup(), checkLoginId(), checkEmail()
MemberDAO: existsLoginId(), existsEmail(), insertMember()

[발표 화면 시연 포인트]
1) 중복된 아이디 입력 시 안내 메시지
2) 비밀번호 형식이 맞지 않을 때 안내 메시지
3) 정상 입력 및 약관 동의 후 회원가입 성공 화면 이동

============================================================
4. 회원가입에서 중점적으로 구현한 부분
============================================================
회원가입에서 특히 신경 쓴 부분은 중복 검사와 비밀번호 처리입니다.

아이디와 이메일 중복 여부는 MemberDAO에서 PreparedStatement를 사용하여 SELECT 쿼리로 확인합니다. 사용자 입력을 SQL 문자열에 직접 이어 붙이지 않고 파라미터로 전달하는 방식입니다.

또한 비밀번호는 그대로 저장하지 않고 MemberService에서 PasswordHasher.hash()를 호출해 해시 처리한 값을 DAO에 전달합니다. DAO는 그 값을 member 테이블의 password_hash 컬럼에 저장합니다.

따라서 회원가입 과정은 단순히 데이터를 저장하는 것이 아니라, 잘못된 입력과 중복 가입을 검사하고 비밀번호 저장 방식까지 고려한 구조입니다.

참고로 PasswordHasher 클래스의 상세 구현은 이번에 첨부한 네 파일에 없으므로 해시 알고리즘의 세부 설정까지 이 자료에서 검증한 것은 아닙니다.

============================================================
5. 회원정보 수정 기능 설명
============================================================
다음으로 회원정보 수정 기능입니다.

사용자가 로그인한 상태에서 마이페이지에 접근하면 Controller는 세션에 저장된 loginId를 확인하고, MemberService의 getMember()를 통해 회원정보를 조회합니다.

사용자가 이름, 이메일, 휴대폰 번호, 우편번호, 주소, 상세주소를 변경하면 /member/memberUpdate.do 요청으로 전달됩니다.

이때 중요한 점은 수정 대상을 사용자가 임의로 입력한 다른 회원의 아이디로 결정하는 것이 아니라, 로그인 세션에서 가져온 loginId를 기준으로 처리한다는 것입니다.

MemberService의 updateMember()는 이름과 이메일, 휴대폰 번호가 비어 있는지 확인하고 이메일과 전화번호의 형식을 검사합니다. 우편번호를 입력한 경우에는 숫자 5자리인지 검사합니다.

특히 이메일 중복 검사는 회원가입과 방식이 조금 다릅니다. 이미 본인이 사용하고 있는 이메일은 그대로 유지할 수 있어야 하므로, existsEmailExceptLoginId()를 통해 현재 로그인한 회원을 제외한 다른 회원이 해당 이메일을 사용하는지 확인합니다.

검증에 성공하면 MemberDAO의 updateMember()가 UPDATE SQL을 실행하여 member 테이블의 이름, 이메일, 전화번호, 우편번호, 주소, 상세주소를 변경하고 updated_at도 현재 시각으로 갱신합니다. SQL에는 status = 'ACTIVE' 조건이 포함되어 있습니다.

수정 성공 시 Controller는 세션에 저장된 이름도 변경하고, 수정 결과 메시지를 세션에 저장한 뒤 마이페이지로 이동합니다. 마이페이지에서 메시지를 한 번 표시한 후 세션에서 제거하는 방식입니다.

[핵심 코드]
MemberController: memberService.updateMember(...)
MemberService: updateMember()
MemberDAO: existsEmailExceptLoginId(), updateMember()

[발표 화면 시연 포인트]
1) 로그인 후 마이페이지에서 기존 회원정보 확인
2) 이름 또는 연락처 변경 후 저장
3) 수정 성공 메시지와 변경된 정보 확인
4) 다른 회원이 사용하는 이메일 입력 시 중복 처리 설명

============================================================
6. DTO와 데이터베이스 처리 방식
============================================================
MemberDTO는 회원번호, 아이디, 이름, 이메일, 휴대폰 번호, 주소, 회원 권한, 회원 상태, 가입일, 수정일 등의 데이터를 담는 클래스입니다.

각 필드는 private으로 선언되어 있고 getter와 setter를 통해 값을 조회하거나 설정합니다.

MemberDAO에서는 DataSourceProvider를 통해 DataSource를 가져오고, JDBC의 Connection, PreparedStatement, ResultSet을 사용해 데이터를 처리합니다.

회원가입에는 INSERT, 회원정보 수정에는 UPDATE, 아이디와 이메일 중복 검사 및 회원정보 조회에는 SELECT가 사용됩니다.

PreparedStatement와 try-with-resources를 사용하여 SQL 파라미터를 바인딩하고, 사용한 JDBC 자원을 자동으로 닫도록 작성했습니다.

7. 구현 특징과 개선할 점
============================================================
이번 기능의 주요 특징은 다음과 같습니다.

첫째, 회원가입과 정보 수정 모두 Service 계층에서 입력값을 검증하여 Controller와 데이터베이스 처리 코드를 분리했습니다.

둘째, 아이디와 이메일의 중복 여부를 확인하고, 정보 수정에서는 현재 회원의 이메일을 중복으로 처리하지 않도록 별도의 조회 메서드를 사용했습니다.

셋째, 비밀번호는 해시 처리한 값을 저장하도록 구현했습니다.

넷째, 회원정보 수정은 로그인 세션의 아이디를 기준으로 수행하고, 수정 결과를 마이페이지에 안내하도록 했습니다.

개선할 점도 있습니다. 현재 제공된 Controller 코드에는 회원가입 처리와 회원정보 수정 요청에 대한 POST 방식 제한이 명시되어 있지 않습니다. 또한 CSRF 토큰 검증은 이 네 파일에서 확인되지 않으므로 실제 서비스 적용 시 별도 필터나 화면 코드까지 점검할 필요가 있습니다.

추가로 회원정보 수정 시 이메일 중복 오류 코드는 Service에서 반환하지만 Controller에는 전용 안내 메시지 분기가 없어 일반 오류 메시지가 나올 수 있습니다. 이 부분을 보완하면 사용자 경험이 개선될 것입니다.

8. 발표 마무리
============================================================
정리하자면, 제가 담당한 회원가입 기능은 입력값 검증, 아이디와 이메일 중복 확인, 비밀번호 해시 처리, 데이터베이스 저장까지 이어지는 과정으로 구현했습니다.

회원정보 수정 기능은 로그인한 회원을 기준으로 기존 정보를 조회하고, 변경된 정보를 검증한 후 데이터베이스에 반영하는 방식으로 구현했습니다.

이번 작업을 통해 Servlet 기반 MVC 구조에서 Controller, Service, DAO, DTO가 어떻게 협력하는지 이해할 수 있었고, 회원 데이터를 처리할 때 유효성 검사와 중복 확인이 중요하다는 점을 배웠습니다.

이상으로 제가 담당한 회원가입 및 회원정보 수정 기능에 대한 발표를 마치겠습니다. 감사합니다.

9. 예상 질문 및 답변 (발표 준비용)
============================================================
Q1. Controller와 Service를 나눈 이유는 무엇인가요?
A1. Controller는 HTTP 요청과 화면 이동을 처리하고 Service는 입력값 검증 및 업무 규칙을 담당하도록 분리하여 유지보수하기 쉽게 하기 위해서입니다.

Q2. 아이디와 이메일 중복 검사는 어떻게 하나요?
A2. Service에서 DAO의 existsLoginId(), existsEmail()을 호출하고, DAO가 member 테이블을 SELECT하여 기존 데이터가 있는지 확인합니다.

Q3. 회원정보 수정에서 본인 이메일을 그대로 사용할 수 있나요?
A3. 네. existsEmailExceptLoginId()는 현재 로그인한 회원의 아이디를 제외하고 이메일 중복을 확인하므로 기존 이메일을 그대로 사용할 수 있습니다.

Q4. 비밀번호를 데이터베이스에 평문으로 저장하나요?
A4. 아닙니다. Service에서 PasswordHasher.hash()를 호출한 결과를 password_hash 컬럼에 저장하도록 구현되어 있습니다.

Q5. 다른 회원의 정보를 수정하지 못하도록 어떻게 처리하나요?
A5. Controller가 로그인 세션에서 loginId를 가져와 해당 회원을 기준으로 수정 요청을 수행합니다. 다만 전체적인 접근 제어 안전성은 다른 설정과 코드도 함께 점검해야 합니다.

Q6. 회원정보 수정 시 데이터베이스에서는 어떤 SQL을 사용하나요?
A6. UPDATE member SET ... WHERE login_id = ? AND status = 'ACTIVE' 형식으로 수정하며 updated_at도 갱신합니다.

Q7. 회원가입에 실패하면 어떻게 되나요?
A7. Service가 오류 코드를 반환하고 Controller가 해당 메시지를 설정한 뒤 회원가입 JSP로 다시 이동합니다. 비밀번호를 제외한 입력값은 다시 전달합니다.

Q8. 개발하면서 개선할 점을 발견했나요?
A8. 회원정보 수정 시 중복 이메일에 대한 전용 오류 메시지 추가, 요청 메서드 제한, CSRF 방어 적용 여부 확인 등이 개선할 부분입니다.
